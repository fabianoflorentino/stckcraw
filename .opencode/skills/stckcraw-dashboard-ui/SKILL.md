# stckcraw dashboard UI

Project-specific workflow for the static dashboard in `docs/`. It captures the
conventions and release ritual already used by this repository.

## Scope

Use for any user-visible frontend change: charts, sparklines, tooltips, search,
wallet/watchlist, favorites, responsive layout, translations, copy, and the
accompanying docs. Backend, crawler or workflow changes still need their own
validation; load the relevant Go skills when touching Go code.

## Non-negotiables

- The site is static: plain HTML, CSS and JavaScript. No frontend framework and
  no charting library.
- Never hand-edit `docs/data/latest.json`; it is generated by the Go crawler.
- Keep the snapshot contract stable unless the Go side is changed and tested.
- Every user-facing string must exist in both `pt-BR` and `en-US` in
  `docs/i18n.js`.
- Do not leave one locale, one viewport or one input method behind.
- Never commit only part of the release ritual: changelog, docs and validation
  are part of the feature.

## Implementation workflow

1. **Read first.** Inspect the existing implementation and reuse its helpers:
   `escapeHTML`, `formatPercent`, `formatPoints`, `formatIndexChartDate`,
   `changeTone`, `isValidWalletSymbol`, `updateWalletStar`, `t`, and the chart
   geometry constants.
2. **Keep the UI native.** Prefer `createElement` and `textContent` for dynamic
   content. When using template strings, escape every interpolated value with
   `escapeHTML`. Never inject raw user or API content into `innerHTML`.
3. **Preserve state conventions.** Browser preferences use `localStorage` keys
   prefixed with `stckcraw:` and wrapped in `try/catch`.
4. **Handle input methods.** Mouse and touch must both work. Use pointer
   events, `pointerleave`/`pointercancel`, and set `touch-action` where needed.
5. **Respect motion.** Any transition or animation must degrade under
   `prefers-reduced-motion`.
6. **Keep data honest.** If a value is interpolated or derived, say so in the
   UI or in `docs/architecture.md`; do not present it as an intraday quote.
7. **Add i18n keys.** Dynamic strings use `t(key, vars)`. Static text uses
   `data-i18n`, `data-i18n-aria`, or `data-i18n-html`. Update both locales.
8. **Accessibility.** Give controls an `aria-label`, preserve focus behavior,
   and keep the underlying values available outside hover-only affordances.

## Chart conventions

- Charts are inline SVG built in `docs/app.js`.
- Keep `CHART_WIDTH`, `CHART_HEIGHT` and `CHART_PADDING` as the single source
  of geometry; do not duplicate magic numbers in new code.
- Points are sorted daily closes; the period change is cumulative from the
  first point.
- Interactive overlays live in HTML next to the SVG when possible, so tooltip
  typography and positioning stay in CSS.
- Validate edge behavior: first/last point, flat series, short series, narrow
  screens, and pointer leaving the plot area.

## Carousel conventions

- The project section uses one native scroll-snap carousel with six cards.
- `--feature-per-view` drives 3 cards on desktop, 2 on tablet and 1 on mobile;
  keep the card count divisible by 3, 2 and 1 when adding cards.
- Navigation is previous/next only: no autoplay and no pagination dots.
- Touch, keyboard, `aria-controls` and `prefers-reduced-motion` must work.

## Release ritual

1. **Changelog, both languages.** Add a new dated section at the top of
   `CHANGELOG.md` and `CHANGELOG.pt-BR.md` for the day the change lands. Use
   `Added` / `Changed` / `Fixed` and `Adicionado` / `Alterado` / `Corrigido`.
   Cover everything user-visible since the previous dated section, including
   CI or deployment fixes that affected delivery.
2. **README.** Update the "O que tem" bullets and the technical summary table
   when behavior, limits or commands change.
3. **Project carousel.** For a user-visible capability, update or add a card in
   the `feature-carousel` in `docs/index.html` and the matching `feature*` keys
   in both locales. Keep the six-card layout so pagination stays aligned.
4. **Architecture.** Update `docs/architecture.md` when a decision, data flow,
   limitation or interaction model changes.
5. **Workflow.** If CI or deploy behavior changed, update the changelog and the
   `.github/workflows/dashboard.yml` description/flow together.

## Validation checklist

Run from the repository root:

```bash
node --check docs/app.js
git diff --check
go test ./...            # when Go, data or workflow behavior changed
golangci-lint run ./...  # when Go code changed
```

Preview locally:

```bash
make preview             # http://localhost:8000
```

For interactive UI, verify in a real browser: open a chart, hover the plot,
check the tooltip at the left/right edges, resize to a phone width, try touch,
and confirm the interaction disappears on pointer leave. Headless Chrome with
the DevTools Protocol works well for repeatable screenshots and assertions.

## Commit and deploy

- Use a conventional commit scoped to the area:
  `feat(site):`, `feat(wallet):`, `fix(site):`, `style(site):`, `docs:`,
  `ci(pages):`.
- Stage only the intended files and inspect `git diff` before committing.
- Pushing to `main` triggers the `dashboard` workflow. Watch the run with
  `gh run watch <run-id> --exit-status` and confirm both `update` and `deploy`
  jobs pass. The Cloudflare step is intentionally `continue-on-error`.
